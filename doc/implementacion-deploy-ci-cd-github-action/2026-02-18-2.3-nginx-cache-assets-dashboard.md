# Nginx — Cache de assets estáticos para el dashboard

**Fecha:** 2026-02-18

## Resumen

Se agrega un bloque `location` en la configuración de Nginx para activar caché de larga duración en los assets estáticos del dashboard (JS, CSS, imágenes, fuentes). El objetivo es reducir el tiempo de carga para usuarios recurrentes evitando peticiones innecesarias al servidor.

## Cambios Principales

- Agregado bloque `location ~* \.(js|css|png|...)$` en el server block de `dashboard.activafitness.com.ar`
- Configurado `expires 1y` para que los archivos se cacheen durante un año en el navegador
- Agregado header `Cache-Control: public, immutable` para habilitar caché en proxies y CDNs

## Flujo de Trabajo

**Primera visita del usuario:**
```
Navegador → solicita main.abc123.js → Nginx responde con el archivo
                                     + header Expires: +1 año
                                     + header Cache-Control: public, immutable
                                     → Navegador guarda en caché local
```

**Visitas siguientes (dentro del año):**
```
Navegador → tiene main.abc123.js en caché → NO hace petición al servidor
                                           → carga instantánea del asset
```

**Cuando el código cambia (nuevo deploy):**
```
React genera main.NEWHASH.js  →  URL diferente  →  no está en caché
                               →  Navegador pide el archivo nuevo al servidor
```

**Punto de entrada:** petición HTTP del navegador a `dashboard.activafitness.com.ar`

**Proceso:** Nginx evalúa la URL contra el patrón de extensiones. Si coincide, agrega los headers de caché antes de servir el archivo desde `/usr/share/nginx/html/dashboard`.

**Resultado:** el navegador almacena el asset localmente y no vuelve a pedirlo hasta que la URL cambie (nuevo hash de build).

## Archivos Afectados

| Archivo | Cambio |
|---------|--------|
| `nginx/conf.d/base.conf` | Agregado bloque `location` con `expires 1y` y `Cache-Control` |

## Notas Técnicas

- **`immutable`:** Le indica al navegador que no intente revalidar el archivo (ni siquiera con `If-None-Match`) durante el período de expiración. Mejora el rendimiento en conexiones lentas.

- **`public`:** Permite que intermediarios como CDNs o proxies reversos también cacheen el archivo, no solo el navegador del usuario final.

- **La regla no afecta a `index.html`:** El archivo `index.html` no tiene hash en su nombre, por lo que no coincide con el patrón y Nginx lo sirve sin caché. Esto garantiza que el navegador siempre obtenga el HTML actualizado con las referencias a los assets correctos.

## ¿Para qué sirve y por qué 1 año?

Cada vez que un usuario abre el dashboard, el navegador hace peticiones al servidor para descargar los archivos JS, CSS, imágenes y fuentes. Sin caché, eso ocurre **en cada visita**, aunque los archivos no hayan cambiado.

Este bloque le dice al navegador: *"guardá este archivo localmente, no lo vuelvas a pedir"*.

### ¿Por qué es seguro cachear durante 1 año?

Es una convención estándar para assets con hash. La lógica es:

**El archivo nunca va a cambiar... pero si cambia, va a tener un nombre diferente.**

Cuando se ejecuta `npm run build`, React genera archivos como:
```
main.3f2a91bc.js   ← el hash depende del contenido
chunk.9d4e2100.css
```

Si se modifica el código y se vuelve a buildear:
```
main.a1b2c3d4.js   ← hash diferente = URL diferente
```

Como la URL cambió, el navegador no tiene ese archivo en caché y lo descarga de nuevo. El caché de 1 año nunca es un problema porque **nunca se reutiliza la misma URL con contenido distinto**. Este patrón se llama *cache busting*.

### Impacto concreto

| Sin caché | Con caché |
|-----------|-----------|
| Usuario abre el dashboard → descarga ~500KB de JS/CSS | Primera visita → descarga ~500KB |
| Usuario recarga o navega → descarga otra vez | Visitas siguientes → 0KB, carga instantánea |
| Usuario vuelve al día siguiente → descarga otra vez | Usuario vuelve al año → sigue usando caché |

Para un gimnasio donde los administradores entran todos los días al panel, el ahorro en tiempo de carga y ancho de banda es significativo.

### La excepción: `index.html`

El `index.html` **no** cae en esta regla porque no tiene hash en su nombre. Nginx siempre lo sirve fresco, y ese HTML contiene las referencias actualizadas a los nuevos archivos con hash. Así funciona el mecanismo completo:

```
index.html (sin caché) → referencia a main.NEWHASH.js → navegador descarga el nuevo JS
```
