# Healthcheck de contenedores Docker

# https://stackoverflow.com/questions/65711938/how-to-use-docker-healthcheck

**Fecha:** 2026-02-24
**Issue:** [#12 — [3.3] Agregar healthcheck a los contenedores](https://github.com/FrancoSeccaspina/proyectoFinal.io/issues/12)

## Resumen

Se implementaron healthchecks en los tres servicios Docker del stack (`activa-db`, `activa-backend`, `activa-nginx`) para que Docker pueda verificar que cada contenedor está operativo antes de iniciar el siguiente. Adicionalmente, se agregó el endpoint `/api/health` en el backend Express como punto de verificación HTTP para el healthcheck del backend.

## Cambios Principales

- Nuevo endpoint `GET /api/health` en `Backend/source/app.ts`
- Bloque `healthcheck` agregado a los tres servicios en `docker-compose.yml`
- `depends_on` actualizado a `condition: service_healthy` en `activa-backend` y `activa-nginx`

## Función del endpoint `/api/health`

El endpoint `GET /api/health` es una ruta minimalista registrada directamente en la instancia `app` de Express, fuera del bloque `app.use('/api', ...)` que agrupa las rutas de negocio:

```ts
app.get('/api/health', (_req: express.Request, res: express.Response) => res.sendStatus(200));
```

**¿Qué hace?**
- Recibe cualquier petición `GET` a `/api/health` y responde inmediatamente con **HTTP 200 OK** sin cuerpo.
- No ejecuta ninguna lógica de negocio ni consulta la base de datos: su único propósito es indicar que el proceso Node.js está activo y respondiendo.
- Al estar registrado antes del middleware `rutaNoEncontrada`, nunca devuelve 404.
- Al no pasar por el bloque `app.use('/api', ...)`, no atraviesa ningún middleware de autenticación JWT, por lo que Docker puede consultarlo sin credenciales.

**¿Para qué sirve en el stack?**
Docker usa este endpoint en el healthcheck del servicio `activa-backend`. Cada 10 segundos ejecuta `wget -qO- http://localhost:3032/api/health`; si recibe 200, el contenedor se marca como `healthy` y Nginx puede arrancar. Si falla cinco veces consecutivas, el contenedor pasa a `unhealthy`.

## Flujo de Trabajo

```
docker compose up
  │
  ├─ activa-db inicia
  │    └─ healthcheck: mysqladmin ping
  │         └─ STATUS = healthy
  │
  ├─ activa-backend inicia (depends_on: activa-db healthy)
  │    └─ healthcheck: wget /api/health → Express responde 200
  │         └─ STATUS = healthy
  │
  └─ activa-nginx inicia (depends_on: activa-backend healthy)
       └─ healthcheck: curl http://localhost/
            └─ STATUS = healthy
```

## Archivos Afectados

| Archivo | Cambio |
|---------|--------|
| `Backend/source/app.ts` | Nuevo endpoint `GET /api/health` antes del middleware 404 |
| `docker-compose.yml` | Bloque `healthcheck` en los 3 servicios; `depends_on` con `condition: service_healthy` |

## Notas Técnicas

- `activa-backend` usa `node:22-alpine` → `wget` disponible vía BusyBox (no `curl`).
- `activa-nginx` usa imagen Debian-based → `curl` disponible.
- `activa-db` tiene `start_period: 30s` para darle tiempo al init de MySQL antes de que empiecen a contar los reintentos.
- `sendStatus(200)` envía el código HTTP sin cuerpo de respuesta, suficiente para que `wget` y `curl -f` lo consideren exitoso.
